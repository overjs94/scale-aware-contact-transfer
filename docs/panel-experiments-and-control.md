# Panel experiment and low-level control

The primary task is **one rigid panel: lift → reorient → seat in a fixed jig →
transfer its weight → release all tools**. The tabletop/leg assembly remains an
auxiliary multi-object demonstration. The new executable is
`contact_transfer.panel_fixture.run_panel`; its URDFs, eight keyframes, source
contacts and controller settings are in `scenarios/panel_fixture` inside the
package. The supplied initial grasp is part of the scenario. Reaching from an
open, remote hand is outside this task.

## What is optimized at small scale?

The previous public tabletop/leg demonstration supplied contact positions and
modes and optimized target reaction forces and joint torques. It did **not** run
source contact-position refinement or network inference.

The panel task now calls `refine_source_and_transfer` before target planning.
Its default input is an explicitly labelled **synthetic contracted fixture**:
a 150 × 100 × 10 mm panel of mass 0.03125 kg, three group IDs and bounded surface
charts. No hand demonstration or neural-network prediction is claimed.
An external contracted result can replace `source_contacts.json` with the same
schema, SI units and object-frame coordinates. `origin` records provenance;
`inference_executed` is input provenance, not evidence that this program ran a
network. Execution reports separately record `network_inference_executed=false`.

For chart coordinates u_i, contact positions p_i(u_i), and source point-contact
reactions λ_ik, the source NLP solves

\[
\min_{u,\lambda,\rho}\;-\rho+\beta\sum_i\|p_i(u_i)-\hat p_i\|^2,
\quad
\sum_i W_i(p_i,R_i)\lambda_{ik}=w_{s,0}+\rho E_sD_s\xi_k,
\quad\lambda_{ik}\in\mathcal C_{P,i},
\]

for every box vertex ξ_k, with chart bounds and a 2 mm displacement bound.
All source contacts use the common P inner model; target gripper capacity is
not used to improve a source score. Normals are fixed in this fixture. The
report contains before/after positions and independently checked Clarabel
SOCP margins. Disabling refinement fixes positions while recomputing the same
source force feasibility problem.

Only geometry transfers:

\[
p_{t,i}=s\,p_{s,i},\qquad n_{t,i}=n_{s,i},\quad s=4.
\]

Source reactions, robustness and mass are **not** transferred. Target mass and
inertia come from `panel.urdf` (600 × 400 × 40 mm, 2 kg); robot parameters and
effort limits come from each robot URDF. A new force/torque allocation is
solved under the target model. Source feasibility does not certify the target. Source and target use different
disturbance scales D, so their numerical margins are not directly comparable.

## Target planning and validation

The reference object pose interpolates supplied keyframes using quintic
translation and SO(3) rotation interpolation. Full-pose IK supplies arm joint
references; finite differences supply velocities and accelerations at planning
nodes. IPOPT allocates nominal contact reactions with rigid-body inertial
balance, contact capability bounds and URDF effort bounds. This is a prescribed
path and mode schedule, **not** articulated contact-implicit trajectory search.

All six-vectors are moment/angular first. λ is object-on-robot. With the mixed
Jacobian Jv=[ω_tool; ṗ_world] and its power-dual λ=[m_tool; f_world],

\[
M_r\ddot q+h_r=\tau+J_r^T\lambda_r,\qquad
M_o\dot V+h_o=-\sum_i W_i\lambda_i+w_{\mathrm{jig}}.
\]

The planned jig load ramps from zero after seating to the panel weight before
release. During execution the jig load is generated by actual collision
contacts, never applied as an artificial object force. The panel has a free
joint; there are no weld/equality attachments or overwritten object poses.
The report measures final jig support, loss of robot contact, keyframe pose
errors, contact retention, force envelopes and actuator torque margin.
Frozen carrying keyframes also receive independent SOCP checks including
robot gravity, Jacobians and effort bounds. The box margin is not an exact
ellipsoidal margin. Mesh checks are sampled; full-geometry certification stays
false. MuJoCo uses collision STL convex hulls and soft contacts; the web viewer
loads the original URDF visual meshes. Both are needed for reproducible review.

## Panda torque control

For e_q=q_d−q and e_v=q̇_d−q̇, the implemented joint/Cartesian controller is

\[
a_c=\ddot q_d+K_qe_q+D_qe_v,
\quad
\tau_c=\operatorname{clip}_{\tau_{\max}}
\{\operatorname{RNEA}(q,\dot q,a_c)-J^T\lambda_{ff}+J^Tw_{pd}\}.
\]

Here w_pd=[K_R Log(RᵀR_d)+D_R( RᵀR_d ω_d−ω);
K_x(p_d−p)+D_x(v_d−v)] uses the same mixed coordinates. The reaction feedforward
is the optimized object-on-robot reaction, transformed to the current tool
frame. Native fingers use a separate gravity plus joint PD torque, with a
closed reference slightly inside the panel surface to establish a squeeze.
All outputs are limited by URDF efforts. Numerical gains and the finite soft
pad torsional friction are in `case.json`; they are simulation assumptions,
not a hardware grasp calibration. No libfranka connection is executed.

## RB5-850E position control

The selected alternative is RB5-850E. Joint position commands are radians in
our interface. `rb_position_command` creates a reviewable payload and performs
explicit radian-to-degree conversion only when requested; it sends nothing to
hardware. The pinned ROS driver itself converts radians to degrees before
calling `move_servo_j`. The same upstream driver also offers effort commands;
position mode here is the requested experiment configuration.

For simulation we declare an inner position servo

\[
\tau_{\mathrm{inner}}=\operatorname{clip}_{\tau_{\max}}
\{K_p(q_{cmd}-q)-K_d\dot q\},
\qquad
q_{cmd}=q_d+K_p^{-1}(\tau_{ff}+K_d\dot q_d).
\]

The latter bias is valid only for the explicitly assumed simulated gains, with
τ_ff=RNEA(q_d,q̇_d,q̈_d)−J_dᵀλ_ff. The actuator receives **positions**, and the
trace records actual actuator forces as torques. For hardware start from q_cmd
=q_d, configure the official streaming interface, identify latency/bandwidth
and torque limits, and only then enable a validated compensation or admittance
loop. The vendor's internal control law/gains are not known from URDF.

The pinned RB5 URDF declares 10 Nm for every joint. This value is preserved and
reported as upstream model data; it has not been identified on hardware. A
rejected large-load trajectory under these limits is a model-level result,
not proof of the physical robot's capacity. Do not inflate these bounds merely
to make an embodiment comparison pass.

## Mobile dual-arm embodiments

G1 is available for URDF kinematics/dynamics preview. It is not yet a validated
mobile manipulation controller. A floating-base extension must solve

\[
M(q)\dot v+h(q,v)=S^T\tau+J_{feet}^Tf_{feet}+J_{hands}^T\lambda,
\]

including the six unactuated base equations, feet friction/support constraints,
COM/balance constraints and contact transitions. Arm IK with a prescribed base
pose does not supply those constraints. Official G1 low commands expose
(q_d,q̇_d,K_p,K_d,τ_ff), corresponding to a joint PD plus feedforward model;
this does not by itself implement standing or locomotion. No G1 hardware path
or balanced mobile execution is claimed here.

https://github.com/unitreerobotics/unitree_sdk2_python/blob/master/example/g1/low_level/g1_low_level_example.py

RBY1 is a **mobile dual-arm manipulator with an actuated wheeled base**. Its
base motion belongs in the task plan and low-level interface. A fixed-base
dual-arm approximation is only a separately labelled baseline. The planned
configuration is

\[
q=(x_b,y_b,\psi_b,q_{\mathrm{torso}},q_L,q_R),\qquad
T_{W,\mathrm{tool},i}=T_{W,B}(x_b,y_b,\psi_b)
T_{B,\mathrm{tool},i}(q_{\mathrm{torso}},q_i).
\]

Thus the same object-frame contracted anchors are realized jointly by base,
torso and arm motion. Base position, heading and motion limits must participate
in reachability and collision checks; the base footprint and load-dependent
stability must also be checked throughout transport and jig seating. Wheel
kinematics and admissible base velocities must come from the official model;
an SE(2) command interface does not justify assuming independent sideways
motion. This wheeled-base model differs from G1's floating-base foot-contact
and balance problem.

The executable `contact_transfer.mobile_panel.run_mobile` now implements a
restricted RBY1-A mobile baseline together with one fixed Panda. The official
SDK/model is pinned to `300a585c297d1bdf8554312c3a1659610a9823f5` and retains its
Apache-2.0 license and NOTICE. Original link mass, COM, inertia, joint origins,
axes and arm effort limits are preserved and independently checked. The vendor
custom capsule proxies are replaced by convex hulls of official per-link OBJ
geometry; original DAE visual meshes remain available in the web viewer.
Parent/grandparent mechanical neighbours are excluded from self-collision.
Native hand visual geometry has no full collision model; the contact tools are
explicitly authored parallel-jaw pads and a spherical support.

The 36-second, nine-keyframe task is: shared lift with the Panda → handover at
6 s → Panda retreats clear → drive from 8 to 24 s → seat on the destination
cantilever jig at 28 s → transfer load → release RBY tools at 32 s. The RBY base
travels 1.4 m along a supplied straight corridor. The torso holds a supplied
ready posture; this is not joint optimization of arbitrary torso/base paths.
The mobile source fixture has its own synthetic anchor placement so G/P
support remains feasible after removing the Panda contact. Source refinement
runs before geometry-only transfer; target forces are recomputed.

At the destination, each RBY contact target is farther from its initial fixed
shoulder than the sum of all intervening URDF joint/tool translation lengths.
This RBY comparison holds the torso at the same ready posture in both
conditions. A separate counterfactual checks the full fixed Panda chain while
keeping its original panel anchor. The report stores the comparison scope,
**geometric reach upper bound**, target distance and
`provably_outside_fixed_base` flag for each arm. This is stronger than a failed
IK seed: an unreachable upper bound rejects the stationary-base alternative.
The moving-base realization also checks the supplied full-pose arm IK path,
velocity/torque bounds and sampled geometry.

The official URDF `<mobile>` element specifies a differential base with wheel
separation b=0.53 m, radius r=0.1 m and wheel axes along local −y. Consequently,
for this sign convention and axle-frame forward/yaw commands,

\[
\dot x=v\cos\psi,\quad\dot y=v\sin\psi,\qquad
\dot\theta_r=-\frac{v+b\omega/2}{r},\quad
\dot\theta_l=-\frac{v-b\omega/2}{r}.
\]

There is no lateral velocity command. The nominal straight path has ψ=0;
its quintic distance profile provides continuous velocity and acceleration.
The simulated controller converts base tracking error to bounded (v,ω), then
uses limited wheel velocity feedback torques. These are the only mobility
actuators. The RBY base is a free body with wheel/floor contacts: neither base
nor panel poses are reset, teleported or prescribed during stepping. Official
chassis support meshes provide low-friction skid contact in place of resolved
passive caster rolling. This assumption is explicit in every report.

Torso/arm position actuators use the declared inner PD model and inverse-PD
feedforward described in the RB section; both hand reactions act on the **same**
RBY joint vector, so their Jacobian-transpose contributions are summed before
imposing the joint torque limits. The Panda uses the torque/Cartesian controller
above. The wheel 40 Nm bound is an authored simulation setting: the upstream
URDF does not specify a wheel effort rating. It is not a manufacturer limit.
Servo gains and grasp wrench bounds are also simulation assumptions. The
planner allocates nominal object/robot inertial wrenches on the supplied path;
it does not optimize floor contact modes or provide a whole-body robustness
certificate. Ground support, roll/pitch, wheel contact, wheel odometry, tool
wrench envelopes, actual base travel and final jig support are measured in
execution. Source margin is not a mobile-base stability certificate.

The SDK exposes joint-position and SE(2)-velocity commands, but this executable
runs simulation only and never connects to hardware. Turning corridors,
obstacle avoidance, optimized torso motion, rolling caster modelling and
hardware validation remain further work. G1 still needs its separate
floating-base foot-contact/balance controller.

The three-arm baseline uses one native gripper and two spherical supports.
A physical dual-arm G/P realization must be checked separately; removing a
support is not automatically feasible. Keep assignment and transition effects
separate in experiment 3. Store dense contacts, group IDs, object-frame anchors,
keyframe poses, source size/mass, target URDF revisions, solver tolerances,
initial seeds, contact settings and measured success criteria for every trial.
